# libmetasec_ml.so 补环境全过程总结

> 目标：在**只给 `arm64-v8a/libmetasec_ml.so` 一个 .so**（外加后来补充的 dex、设备参数、
> 一条真实抓包请求）的前提下，用 **unidbg** 把这个库跑起来，对给定 `video_id` 产出番茄小说
> 请求所需的 6 个安全头（`x-khronos / x-gorgon / x-ladon / x-argus / x-medusa / x-helios`）。
> **只补环境、不分析/不实现任何 native 协议算法**——签名值全部由库自己计算，我们只负责把它
> "骗"到能正常运行、并主动调用到签名入口。
>
> 本文按"踩到的坑 → 现象 → 排查思路 → 根因 → 解决办法"的顺序，记录整个过程中遇到的每一个
> 关键问题。最终成果是一个无需 maven、下载即可在 Windows 跑出 JSON 的自包含工程（见 `README.md`）。

---

## 0. 整体认知：这个库长什么样

动手前先把目标摸清楚，避免方向错误：

- `libmetasec_ml.so`：3.9MB，ByteDance metasec / Argus SDK 的 native 部分（番茄 7.2.4.32，
  versionCode 72432，与抖音同代签名库）。
- `readelf -d` / 导出表：**只导出一个 `JNI_OnLoad`**。所有 JNI 方法都是**运行时动态注册**的，
  不是静态导出。
- `strings` 几乎读不到有意义的字符串——字符串都是**运行时解密**的，所以**静态分析读不出**
  它要回调哪些 Java 类、要哪些参数。

**第一个结论（也是方向性的）**：这种库**不可能靠静态阅读补出来**，必须用 unidbg **真的把它跑
起来**，让它在运行中把"我需要什么环境"一项项暴露出来，缺什么补什么。

## 1. 坑①：JNI_OnLoad 里 `GetSuperClass(java/lang/Object)` 直接抛异常崩溃

**现象**：刚 `loadLibrary` + `callJNI_OnLoad`，unidbg 立刻抛 `BackendException` 终止，
栈停在 `DalvikVM64` 的 `GetSuperClass`。

**排查**：开 `vm.setVerbose(true)` 看 JNI 调用流水，发现库在 OnLoad 早期对
`java/lang/Object` 调了 `GetSuperClass`。

**根因**：按 JNI 规范，`GetSuperClass(Object)` 应当**返回 NULL**（Object 没有父类）。
但 unidbg 这个版本的实现里，遇到 Object（以及 superclass 取不到）时是 `throw new
BackendException()`——直接把模拟器干崩了。这是 unidbg 自身的一个 bug / 不符合规范之处。

**解决**（`unidbg-patches.diff` 第 3 处，`DalvikVM64.java`）：把这两处 `throw new
BackendException()` 改成 `return 0`（即返回 NULL jclass），符合 JNI 规范：
```java
if (dvmClass.getClassName().equals("java/lang/Object")) {
    return 0;          // was: throw new BackendException();
}
DvmClass superClass = dvmClass.getSuperclass();
if (superClass == null) {
    return 0;          // was: throw new BackendException();
}
```
改完 OnLoad 不再因这一步崩溃。

## 2. 坑②：native↔Java 的回调全走一个分发器 `MS.b(cmd, …)`，要逐个 cmd 应答

**现象**：OnLoad 往下走，库开始通过 JNI 反向回调 Java 静态方法
`com.bytedance.mobsec.metasec.ml.MS.b(int cmd, int, long, String, Object)`，
向"宿主 App"要各种环境/配置数据。不应答它就拿不到想要的东西、流程卡住。

**排查思路**：这正是"native 是半成品、另一半在 App 的 Java SDK 里"的体现。于是反编译用户提供
的 dex（`classes17.dex` / `classes23.dex` 里的 `com.bytedance.mobsec.metasec.*`、`ms.bd.*`），
照着真实 SDK 看每个 cmd 该返回什么，在 harness 里**复刻**（这是读 Java、补环境，不是逆向 native）。

**解决**（`MetasecDump.dispatch()`）：按 cmd 应答，例如：
| cmd（十进制） | 含义 | 应答 |
|---|---|---|
| 268435470 | GetABSwitch | `2L` |
| 268435471 | GetDelayTime | `0L` |
| 268435458/459 | | `"np"` |
| 268435463 | | `"[]"` |
| 268435464 | | `"null[<!>]null[<!>]0[<!>]"` |

同时补齐库在初始化中用到的一批 JNI 回调：`Context.getPackageName/getFilesDir/getCacheDir`、
`System.getProperty(os.arch/os.version/...)`、`Boolean/Integer/Long.valueOf` 自动装箱等
（见 `callObjectMethodV` / `callStaticObjectMethodV`）。缺啥补啥，跑一遍报一个新缺口，补上再跑。

## 3. 坑③：worker 线程 spawn 时 `tgkill` 自发信号把模拟器打崩

**现象**：OnLoad 中库会 `clone` 出 3 个 worker 线程互相用 futex 同步。线程一起来就触发
`tgkill(tgid, tid, sig)` 给自己/同组线程发信号，unidbg 的信号派发路径随即抛异常崩溃。

**排查**：日志显示崩溃点在 `AndroidSyscallHandler.tgkill` → `sendSignal` →
`ThreadContextSwitchException` 这条线上。库其实只是用信号做线程内部协调，我们并不需要真的把
信号语义实现得完美。

**根因**：unidbg 的线程调度器对这种"自发信号"处理不健壮，而我们对信号的真实语义并无需求。

**解决**（`unidbg-patches.diff` 第 2 处，`AndroidSyscallHandler.tgkill`）：加一个开关，
在 `unidbg.tgkill.drop=true` 时**直接吞掉信号返回 0**：
```java
if ("true".equals(System.getProperty("unidbg.tgkill.drop"))) {
    return 0;
}
```
`run.bat` / `run.sh` 默认带上 `-Dunidbg.tgkill.drop=true`。加上后 3 个 worker 线程能正常
spawn 并用 futex 互相同步，不再崩。

## 4. 坑④（最硬的核心）：库检测到模拟器，**拒绝 RegisterNatives 签名函数**

**现象**：环境补到库"看起来"初始化完成了，但要调用签名函数时永远 `find method failed`——
签名函数 `ms/bd/c/y2.a` 始终没有被注册。在**整个运行日志里 grep `RegisterNatives`，
一次都没有出现**。

**排查与根因（关键洞察）**：
- 反汇编确认，这个版本的签名函数**不是在 JNI_OnLoad 里注册**的，而是由 worker 线程在初始化
  时**懒注册（lazy RegisterNatives）**。
- worker 线程 spawn 后，会先做一圈"自己是不是跑在模拟器里"的环境检测；**一旦觉得环境可疑，
  它就静默地不去执行那次 RegisterNatives**，然后停在 futex 上。
- 也就是说：`y2.a` 永远注册不上，**不是我环境补得不够，而是该版本 metasec 的反模拟自保护设计**。
- 查公开资料（看雪 290392「最新版抖音 unidbg 生成 7 神」、289870）佐证：同代 metasec 在
  unidbg 下**没人靠"让库自己注册"跑通**；公认可行的唯一做法是——**先静态/动态定位签名分发函数
  在 .so 里的偏移，再在 unidbg 里按偏移"直接调用/手动绑定"那个函数**，绕过被反模拟拦截的自注册。

**解决**（A 方案，经用户同意可逆向定位入口）：
1. **静态定位入口偏移**：在 `libmetasec_ml.so` 里定位签名分发函数 `ms/bd/c/y2.a` 的 JNI
   trampoline，确定其入口为 `base + 0x26e684`（只定位入口，不分析其内部算法）。
2. **手动绑定**：unidbg 的 `DvmClass` 用一个私有 `nativesMap` 存"方法签名 → 函数指针"。
   既然库自己不注册，就用反射把这一项**手动塞进去**，让 `callStaticJniMethod*` 能像调用一个
   正常注册的 native 那样派发到它：
   ```java
   Field f = DvmClass.class.getDeclaredField("nativesMap");
   f.setAccessible(true);
   ((Map<String,UnidbgPointer>) f.get(y2))
       .put("a(IIJLjava/lang/String;Ljava/lang/Object;)Ljava/lang/Object;",
            UnidbgPointer.pointer(emulator, base + 0x26e684));
   ```
   这样我们就**绕过了被反模拟拦截的自注册流程**，但函数体本身（真正的签名算法）原封不动由库自己跑。

> 这一步是整个项目能否成立的分水岭：在确认"库故意不注册"之后，方向从"继续补环境逼它自己注册"
> 转为"手动把已存在的函数挂上去直接调"。

## 5. 坑⑤：worker 线程需要被"泵"动，否则懒初始化没跑完

**现象**：手动绑定 `y2.a` 后直接调用，仍因为 SDK 内部状态没初始化完而拿不到正确结果。

**根因**：很多初始化工作是在 worker 线程里完成的，主线程 `callJNI_OnLoad` 返回 ≠ 初始化完成。

**解决**（`MetasecDump.main`）：
- `emulator.getSyscallHandler().setEnableThreadDispatcher(true)` 打开线程派发；
- `emulator.getBackend().registerEmuCountHook(100000)` 做**抢占式线程切换**（每 N 条指令切一次
  线程），让 OnLoad 里 spawn 的 worker 线程能和主线程交替执行；
- `emulator.getThreadDispatcher().runThreads(15, SECONDS)` 把 worker 线程"泵"到稳定态。
这是 unidbg 处理多线程库的经典 `ThreadTest` 套路。

---

## 6. 坑⑥：n3 静态初始化要读一个特定环境变量

**现象**：初始化链路里某处（`ms.bd.c.n3` 一类）会去读一个名字很奇怪的环境变量，读不到就走异常分支。

**排查**：从回调/崩溃点反推，发现它在 `getenv` 一个形如 `28d7fdd567361198183fa7b8e` 的 key。

**解决**（`unidbg-patches.diff` 第 1 处，`AndroidElfLoader.java` 的初始 environ 列表里加一项）：
```java
"NO_ADDR_COMPAT_LAYOUT_FIXUP=1",
"28d7fdd567361198183fa7b8e=a7"     // 新增
```
注入这个环境变量后，该静态初始化走正常分支。

## 7. 坑⑦：找对"签名入口 cmd"和正确的调用序列

**现象**：`y2.a` 是个统一分发器 `a(int cmd, int, long, String, Object)`，不同 cmd 做不同事。
随便调一个 cmd 不会直接吐出 6 个头——必须按 SDK 真实的"初始化→配置→取句柄→塞设备号→签名"
顺序走，否则要么返回 null、要么签名无效。

**排查思路**：对照反编译出的 `com.bytedance.mobsec.metasec.core.g` / `ms.bd.c.*` 的调用链，
把每一步对应到 `y2.a` 的哪个 cmd、传什么参数，逐一复刻。

**解决**（`MetasecDump.main` 里的驱动序列）：
| 步骤 | cmd（十进制） | 作用 |
|---|---|---|
| 字符串解密 smoke | 16777217 | 解出 `d4.a`（版本串 `v04.09.09.01-bugfix`），验证调用通路 |
| context init | 16777219 | 传入伪造的 `Context` |
| register config | 67108865 | 传一个 JSON 数组：aid=8662、license、channel、d4.a、device_id… |
| get handle | 67108866 | 取得 SDK 句柄 |
| setDeviceID | 33554434 | 把 device_id 压到句柄上 |
| setInstallID | 33554435 | 把 install_id 压到句柄上 |
| **getFeatureHash** | **33554438** | **真正产出 6 个安全头**，入参 = `(url, body)` |

设备/应用参数（aid、license、channel、device_id、install_id 等）来自用户给的真实抓包请求 +
`MSConfig`。`getFeatureHash` 的入参就是**整条 HTTP 请求的 url（含 query）+ body**——这也印证了
一开始的判断：**这 6 个头是对"整条请求"的签名，不是单纯 video_id 的函数**。

## 8. 坑⑧：返回的 header 值被多包了一层引号（DvmObject.toString）

**现象**：`getFeatureHash` 返回一个字符串数组（key/value 交替）。直接打印时，value 外面莫名其妙
多了一对引号，拼进 JSON 后变成双重引号、值也不对。

**根因**：数组元素是 unidbg 的 `DvmObject`/`StringObject` 包装对象，直接 `String.valueOf` /
`toString` 会带上包装层的格式（多一层引号），而不是里面真正的字符串。

**解决**（`MetasecDump.asStr()`）：写一个解包器，把 `DvmObject` 里的 `getValue()` 取出来再转
String，避免多包引号：
```java
if (o instanceof DvmObject) {
    Object inner = ((DvmObject<?>) o).getValue();
    if (inner instanceof String) return (String) inner;
    ...
}
```
另外因为 unidbg classpath 上没有 `org.json`，自己写了个最小 `jq()` 做 JSON 字符串转义，
最后输出一行稳定的 `__HEADERS_JSON__{...}` 供 Python 解析。

## 9. 坑⑨：时间戳一致性——怎么证明"签名管线真在跑、而且对"

**问题**：6 个头里 5 个都带一次性随机 nonce，每次运行都不一样，没法和历史抓包逐字节对比，
那怎么证明我们没跑错？

**思路**：抓住唯一确定性的量——`x-khronos` 就是请求时间戳。只要把模拟器时钟**钉死**到用户抓包
那一刻，如果 `x-khronos` 能**逐字节复现**用户的参考值，就证明：① 函数真在跑；② 时间等输入喂对了；
③ 整条签名管线正确。

**解决**（`unidbg-patches.diff` 第 4 处 + `currentTimeMillis` 覆写）：加 `unidbg.fake.time.ms`
系统属性，覆写 `AndroidSyscallHandler.currentTimeMillis()` 返回钉死的时间：
```java
String fake = System.getProperty("unidbg.fake.time.ms");
if (fake != null && !fake.isEmpty()) return Long.parseLong(fake);
```
**实测**：`FAKE_TIME=1782306314000` 时，`X-Khronos = 1782306314`，与用户抓包参考值
**逐字节一致**。✔ 铁证。

## 10. 坑⑩：端到端真实请求——header 顺序、x-ss-stub、brotli、cookie

到这一步 harness 已经能稳定吐 6 个头。最后要把它对接成"换时间戳→重新签名→真的请求到 JSON"。
为此写了 `orchestrate.py`，又踩了几个网络层的坑：

- **header 顺序**：HTTP/2 下 header 顺序敏感。`orchestrate.py` 严格按抓包顺序构造
  （cookie → 标准头 → `x-argus … x-medusa`），用 `httpx` 的 HTTP/2 client 发送。顺序错了
  服务端可能直接拒。
- **x-ss-stub = MD5(body)**：抓包里给的 `x-ss-stub` 是请求体的 MD5。我们换了时间戳但 body 不变，
  直接**自己算 `MD5(body)`** 填进去，服务端接受。
- **每次时间戳要新鲜**：`x-khronos` / `_rticket` 用**当前时间**实时生成，否则服务端因时间戳过期
  拒绝。生成时间戳 → 喂给 harness（通过 `-Dreq.url.file`/`-Dreq.body.file` 注入新 url/body，
  无需重新编译）→ 出 6 头 → 组装发送。
- **brotli 响应**：接口返回 `content-encoding: br`，需要 `brotli` 解码才能读到 JSON
  （`requirements.txt` 里带了 `brotli`，并在解码处做了回退）。
- **cookie / 鉴权会过期**：内置 cookie（`odin_tt`、`passport_csrf_token` 等）是抓包设备的会话
  凭据。若过期，服务端可能即使签名正确也因鉴权失败而拒（从返回码可与"签名错误"区分）。这点在
  README 里也提醒了用户，过期就换自己的新 cookie。

**最终结果**：`python orchestrate.py` → 服务端返回 **HTTP/2 200 + 完整 JSON**
（含 `data.video_model` → `video_list` → `main_url`），`{"BaseResp":{"StatusCode":0},"code":0}`，
打印 `VERDICT: PASS`。**签名被真实服务端接受，协议模拟通过。** 每次换时间戳重跑都通过。

## 11. 坑⑪（Windows 实机才暴露）：`NetLinkSocket` 对未知 netlink 类型抛异常 → 掉进调试器假死

这个坑在我自己的 Linux 机器上一直没出现，是用户在 **Windows 实机**跑时才暴露的，很有代表性。

**现象**：`python orchestrate.py` 打印完 `[*] driving unidbg harness ...` 后**长时间无任何输出、像卡死**
（超过 2 分钟还没结果）。因为 `orchestrate.py` 把 harness 的 stdout 全缓存、只在结束时打印，所以
表面看不出在干嘛。让用户**单独直接跑 `run.bat`** 看实时日志，才抓到真正的报错：

```
java.lang.UnsupportedOperationException: buffer=..., count=8192, netlinkType=0x1a
        at com.github.unidbg.linux.file.NetLinkSocket.handleType(NetLinkSocket.java:140)
        at com.github.unidbg.linux.file.NetLinkSocket.read(NetLinkSocket.java:56)
        ...
        at MetasecDump.main(MetasecDump.java:323)
debugger break at: 0x1259a434 ...   <-- 紧接着是一大段寄存器/反汇编 dump
```

**根因**：签名时，库会开一个 **NETLINK socket** 去查网卡/路由表做设备指纹。unidbg 自带的
`NetLinkSocket` 只实现了 `RTM_GETADDR(0x16)`（查地址）这一种应答，遇到 `0x1a`（`RTM_GETROUTE`，
查路由表）就**抛 `UnsupportedOperationException`**。异常在 emulate 过程里抛出后，unidbg 触发了它的
**交互式调试器**（日志末尾那段寄存器/反汇编 dump），调试器在**等 stdin 输入** → 进程就停在那儿不动，
看起来就是"卡死"。

为什么我这边没遇到、用户 Windows 遇到了：库**是否发出 `RTM_GETROUTE`，取决于本机的网络环境**
（网卡数量、路由表条目不同会走到不同分支）。这类"跟宿主机环境相关"的坑，只有在更多机器上跑才会冒出来。

**解决**（`unidbg-patches.diff` 第 5 处，`NetLinkSocket.java`）：给 `handleType` 加一个**兜底**——
遇到没有专门实现的 netlink 类型（如 `RTM_GETROUTE`）时，**回一个空的 `NLMSG_DONE`**（等于"路由表 dump 结束、
没有更多条目"），让库收到一个合法的"空结果"继续往下跑，而不是抛异常进调试器：

```java
// 兜底：未专门处理的 netlink 类型 → 回 NLMSG_DONE（空 dump），别抛异常
final short NLMSG_DONE = 0x3;
ByteBuffer done = ByteBuffer.allocate(20).order(ByteOrder.LITTLE_ENDIAN);
done.putInt(20);                 // nlmsg_len
done.putShort(NLMSG_DONE);       // nlmsg_type
done.putShort(NLM_F_MULTI);      // nlmsg_flags
done.putInt(netlinkSeq);
done.putInt(emulator.getPid());
done.putInt(0);                  // payload: error=0
byte[] doneMsg = done.array();
if (count >= doneMsg.length) {
    buffer.write(0, doneMsg, 0, doneMsg.length);
    this.netlinkType = -1;       // 下一次 read 直接返回 -1，不会死循环
    return doneMsg.length;
}
```

**验证**：单写了个最小用例，构造一条 `netlinkType=0x1a` 的请求喂给 `NetLinkSocket.read`——修复前抛异常，
修复后返回 20 字节、`nlmsg_type=3`（`NLMSG_DONE`），再 read 一次返回 `-1`（不死循环）。整包端到端重跑，6 个头照常产出、
`__HEADERS_JSON__` 正常。

> 顺带的体验改进经验：`orchestrate.py` 把子进程输出全缓存、结束才打印，导致"在跑"和"卡死"无法区分。
> 排查这类问题时，**让用户绕过 wrapper 直接跑底层脚本看实时日志**是最快的定位手段。

## 12. 坑⑫（Windows 实机才暴露，紧接坑⑪之后）：读 `Settings.System.SCREEN_BRIGHTNESS` 时 unidbg 没有该静态字段 → 抛异常掉进调试器

坑⑪的 netlink 补丁生效后，用户 Windows 上 harness 顺利跑过路由表查询、跑完整个初始化、进到**真正的签名阶段**，
但又在更深一层崩了（日志）：

```
JNIEnv->GetStaticFieldID(android/provider/Settings$System.SCREEN_BRIGHTNESS:Ljava/lang/String;)
java.lang.UnsupportedOperationException: android/provider/Settings$System->SCREEN_BRIGHTNESS:Ljava/lang/String;
        at com.github.unidbg.linux.android.dvm.AbstractJni.getStaticObjectField(AbstractJni.java:103)
        ...
        at MetasecDump.main(MetasecDump.java:323)
debugger break at: 0xfffe0964
```

**根因**：签名时库会读 `Settings.System.SCREEN_BRIGHTNESS`（屏幕亮度，设备指纹的一部分）。
`AbstractJni.getStaticObjectField` 对没有内置值的静态字段**直接抛 `UnsupportedOperationException`**，
于是又掉进 unidbg 交互式调试器 → 同坑⑪一样"假死"等 stdin。

为什么这次和坑⑪同样是"环境没补全"，却换个地方：库的设备指纹采集是**多来源拼装**的，netlink（路由表）只是其一，
`Settings` 系统设置（亮度、超时、ANDROID_ID 等）是另一来源。坑⑪让 netlink 那条路通了，执行就推进到了
`Settings` 这条路，于是暴露出下一个缺失项。

**和坑⑪的关键区别**：坑⑪要改 unidbg 源码（`NetLinkSocket` 在 jar 里），坑⑫只需改 **harness 本身**
（`MetasecDump extends AbstractJni`，运行时由 `run.bat` 现编），所以**不用重编 jar**，改 `src/MetasecDump.java` 即可。

**解决**（`src/MetasecDump.java`，纯补环境、不碰签名算法）：在 harness 里 override 三个 JNI 入口，给
`Settings.{System,Secure,Global}` 这组指纹采集兜底——

```java
// 1) 静态字段名常量：返回众所周知的 setting key 字符串
@Override public DvmObject<?> getStaticObjectField(BaseVM vm, DvmClass c, String sig) {
    switch (sig) {
        case "android/provider/Settings$System->SCREEN_BRIGHTNESS:Ljava/lang/String;":
            return new StringObject(vm, "screen_brightness");
        case "android/provider/Settings$Secure->ANDROID_ID:Ljava/lang/String;":
            return new StringObject(vm, "android_id");
        // SCREEN_BRIGHTNESS_MODE / SCREEN_OFF_TIMEOUT 同理…
        default: return super.getStaticObjectField(vm, c, sig);
    }
}
// 2) Settings.*.getInt(resolver, key[, def]) -> 返回一个合理默认值（同时避免无默认重载抛 SettingNotFoundException）
@Override public int callStaticIntMethodV(...) { if (sig 以 Settings$*->getInt( 开头) return 102; ... }
// 3) Settings.*.getString(resolver, key[, ...]) -> 返回空串（在 callStaticObjectMethodV 里）
```

为什么返回任意默认值是安全的：这些值只喂进**每次新鲜生成**的指纹/签名头（x-argus/x-medusa 等），
服务端校验的是"这套头是否自洽、时间戳是否新鲜"，而不是逐字节比对某个真实设备的亮度。坑⑨已用可复现的
`x-khronos` 证明了签名管线本身是对的；指纹来源给个 sane default 不影响服务端接受。

**验证**：Linux 这边整包端到端重跑，6 个头照常产出、`__HEADERS_JSON__` 正常、无回归
（Linux 不走 `Settings` 这条路，所以这段 override 是给 Windows 那条路兜底用的——又一个"跨机器才暴露"的坑）。

## 13. 工程化：从"要装 maven 编译 unidbg"到"下载即可跑"

最初的交付要求用户自己 clone unidbg、`git apply unidbg-patches.diff`、用 maven 编译。为了让
Windows 用户**零编译**就能跑，做了自包含打包：

  所有 jar，运行时只用 `javac` 编译那一个 `MetasecDump.java`，**不再需要 maven、不需要联网**；

`unidbg-patches.diff` 仍保留在包里**仅供查阅**——补丁已经编译进 `deps/` 的 jar，不需要再手动 apply。

## 14. 坑⑬（紧接坑⑫之后）：设备指纹采集会逐个探测大量 JNI 字段/方法 → 改"逐个补"为"统一兜底"

坑⑫给 `Settings.SCREEN_BRIGHTNESS` 兜底后，用户 Windows 日志显示补丁**确实生效**了
（`SCREEN_BRIGHTNESS` 成功返回 `"screen_brightness"`、`getInt` 返回 102），但紧接着又崩在
**下一个**指纹来源：`android/media/AudioManager->STREAM_SYSTEM:I`——一个**静态 int 字段**，
走的是 `getStaticIntField`，而坑⑫只补了对象字段（`getStaticObjectField`）和方法，没覆盖到 int 字段。

**这暴露了一个方法论问题**：这个库的"完整设备指纹采集"会**逐个探测**一长串字段/方法
（屏幕亮度→音量→AudioManager 各 stream→可能还有传感器/电话/Wifi…），而且**这条分支是否被走到，
取决于宿主机环境**（被 unidbg 透传的真机网卡/路由等信息）和库内部的采样判定。开发机（Linux）上
这条分支根本没被触发（我贴过的 Linux 日志里 `Settings` 出现 **0 次**），所以**没法在本地复现**用户
那条路——之前几个补丁对这条路都是"盲修"：能确认不破坏正常路径，但没法本地验证。一个字段一个字段地补，
就得跟用户来回好多轮。

**解决（`src/MetasecDump.java`，思路换成"统一兜底"）**：把 harness 里所有可能被指纹采集命中的
JNI 入口都包一层 try/catch——遇到 unidbg 没实现、本会抛 `UnsupportedOperationException`
（→ 掉进交互式调试器假死）的字段/方法，改成**记一条 `[stub]` 日志 + 返回类型对应的默认值**：

```java
// 通用兜底：任何未实现的 静态/实例 字段/方法 都不再抛异常掉进调试器
@Override public int getStaticIntField(...)      { /* AudioManager.STREAM_* 给真实常量；其余 */ return stubInt(...); }
@Override public int callIntMethodV(...)         { /* getStreamVolume=7 / getStreamMaxVolume=15 ; 其余 */ return stubInt(...); }
@Override public DvmObject<?> getStaticObjectField(...) { /* Settings.* 同坑⑫；其余 String 字段→"" ，否则 null */ }
@Override public DvmObject<?> callObjectMethodV(...)    { /* Context.getSystemService→返回对应 manager 桩对象；其余兜底 */ }
// callStaticObjectMethodV / callStaticIntMethodV / callBooleanMethodV / callStaticBooleanMethodV
// / callLongMethodV / getStaticLongField / callStaticVoidMethodV 全部同样包一层 try/catch
private int stubInt(String sig, IntSup real){ try { return real.get(); } catch(UnsupportedOperationException e){ return 0; } }
```

这样**不管它探测哪个字段/方法都不会再崩**，从"逐个打地鼠"变成"一次兜住一整类"。代价是这些指纹是
默认值而非真机值，但理由同坑⑫：只喂进每次新鲜生成的头，服务端校验自洽性+时间戳新鲜度，不逐字节比对指纹。

**诚实的边界**：Linux 端到端重跑确认**正常路径无回归**（6 个头照常产出、`__HEADERS_JSON__` 正常），
但**这次没有、也无法在本地复现 Windows 那条指纹分支**——兜底是"保证任何探测都不崩"的安全网，
真正能不能跑完那条路，要看用户 Windows 实机日志。

## 14b. 坑⑭（紧接坑⑬之后）：`System.currentTimeMillis()` 走 JNI 静态 long 方法，兜底没覆盖到

坑⑬的统一兜底生效后，用户 Windows 日志一路冲过了 `SCREEN_BRIGHTNESS`、`AUDIO_SERVICE`、
`STREAM_SYSTEM`、`getStreamVolume`（全部成功返回），最后崩在签名取时间这步：

```
java.lang.UnsupportedOperationException: java/lang/System->currentTimeMillis()J
    at AbstractJni.callStaticLongMethodV(AbstractJni.java:583)
    at MetasecDump.main(MetasecDump.java:483)
```

**根因**：坑⑬把"静态/实例的 object/int/boolean 字段方法 + 实例 long 方法 + 静态 long 字段"都兜了，
唯独漏了 **`callStaticLongMethodV`（静态 long 方法）**。而库在签名时正是用 JNI 调
`System.currentTimeMillis()` 取墙上时间（用来算 x-khronos）。注意这条 JNI 取时间路径和坑④里
patch 的 `AndroidSyscallHandler.currentTimeMillis()`（syscall 路径）是**两条不同的路**——
syscall 那条早就 patch 了，JNI 这条之前没人走到，所以一直没暴露。

**解决（`src/MetasecDump.java`，补上 `callStaticLongMethodV` 覆写）**：
```java
@Override public long callStaticLongMethodV(...) {
    if ("java/lang/System->currentTimeMillis()J".equals(signature)) {
        String fake = System.getProperty("unidbg.fake.time.ms");   // 与 syscall 时钟同源
        return (fake!=null && !fake.isEmpty()) ? Long.parseLong(fake) : System.currentTimeMillis();
    }
    if ("java/lang/System->nanoTime()J".equals(signature)) { ... }
    try { return super.callStaticLongMethodV(...); }
    catch (UnsupportedOperationException e) { return 0L; }   // 同坑⑬的统一兜底
}
```
关键点：JNI 取的时间要和 syscall 时钟**同源**——都认 `unidbg.fake.time.ms`，没设就都用真实"现在"，
这样 `FAKE_TIME` 钉时复现 x-khronos 时两条时钟才一致，正常跑时 x-khronos 才"新鲜"。

**诚实的边界**（同坑⑬）：Linux 端到端重跑确认无回归（6 个头照常产出、`__HEADERS_JSON__` 正常），
但 Linux 不走这条 JNI 取时间分支，所以这条补丁仍是"盲修"——真正能否跑完要看用户 Windows 日志。

## 14c. 坑⑮（紧接坑⑭之后）：`newObjectV` 构造 IntentFilter 没兜底 → 改"事后补类型"为"穷举所有 JNI 入口一次性兜全"

坑⑭补上静态 long 方法后，用户 Windows 日志又往前冲了一段，崩在：

```
java.lang.UnsupportedOperationException: android/content/IntentFilter-><init>(Ljava/lang/String;)V
    at AbstractJni.newObjectV(BaseVM, DvmClass, String, VaList)
```

= 设备指纹采集要 new 一个 `IntentFilter`（给充电/USB 广播接收器用）。`newObjectV`（JNI 构造对象入口）
我之前没覆写，又抛异常掉进调试器。

**用户在这里明确叫停了"一个一个补"**：「我不知道后面还有多少坑啊，一个个处理不是事啊」。这是对的——
坑⑬/⑭/⑮ 暴露出同一个本质：unidbg 的 `AbstractJni` 把每个 native JNI 回调都分发到一个
**带 String 签名**的变体（`getXField` / `callXMethod[V]` / `newObject[V]` / `allocObject` / `setXField`），
这些 String 变体默认全部 `throw UnsupportedOperationException`。我每次只补"这次崩的那一种类型"，
下一种类型（静态 long、构造对象……）必然又冒出来。

**这次的做法：穷举 + 自检，一次性兜全。**

1. 通读 `AbstractJni`，列出**所有** String 签名的 JNI 入口（共 53 个），在 `MetasecDump` 里**全部覆写**——
   每个都 `try super → catch UnsupportedOperationException → 返回该类型默认值`（object→null/""、数值→0、
   boolean→false、void→noop）。构造类（`newObjectV`/`newObject`/`allocObject`）特殊处理：返回一个
   **非空**的 stub 实例（`dvmClass.newObject(null)`），因为 native 会拿着这个引用继续调它的方法，
   返回 null 会让后续调用没有接收者。

2. 写了一个**反射自检** `test/JniCoverageTest.java`：枚举 `AbstractJni` 上所有 String 签名 JNI 入口，
   逐个断言 `MetasecDump` 已覆写。这个测试**不需要 .so、不需要真跑、任何机器都能跑**，所以能在 Linux 上
   直接证明"兜底网是完整的"，不必再靠用户那边一轮轮试错来发现漏网类型。第一次跑就抓出我漏的
   `setStaticDoubleField`，补上后 53/53 全过：

   ```
   [JniCoverageTest] String-signature JNI entry points: 53
   [JniCoverageTest] PASS - all 53 entry points overridden by MetasecDump
   ```

**为什么这次比坑⑬/⑭更彻底**：坑⑬/⑭ 是"崩了哪种类型就补哪种"，是事后追赶；这次是"把 AbstractJni 的
入口集合穷举出来，且用机器可验的测试钉死覆盖完整性"，是事前兜全。只要库探测的东西仍走标准 JNI 入口，
就不会再掉进调试器。

**诚实的边界**（同坑⑬/⑭）：Linux 端到端重跑无回归（6 头照常产出、`__HEADERS_JSON__` 正常），但 Linux
本机仍不走这条设备指纹深探分支（日志里 0 条 `[stub]`），所以"返回默认值后库能否语义上继续跑完"这一点，
最终仍需用户 Windows 实跑确认。但"无论探测什么 JNI 入口都不再崩进调试器"这个不变式，已被 `JniCoverageTest`
在本地证明成立。

## 15. 关键经验小结

1. **方向判断比蛮力重要**：一开始就认定"字符串运行时解密 + 动态注册 ⇒ 必须真跑、不能静态读"，
   省掉了大量无用的静态分析。
2. **崩溃要分两类**：unidbg 自身 bug（GetSuperClass、tgkill）→ 打补丁修；库主动的环境检测/反模拟
   （拒绝 RegisterNatives）→ 不能硬刚，改用"手动绑定入口偏移直接调用"。
3. **"库故意不做某事"是常见反模拟手段**：`RegisterNatives` 一次都不出现，是判断"它在防模拟器"的
   决定性信号；公开资料佐证了"按偏移直调"这条路。
4. **确定性的量是验证的锚点**：在一堆随机 nonce 里，用可复现的 `x-khronos`（时间戳）证明管线正确。
5. **全程只补环境、不碰算法**：5 处 unidbg 补丁都是修健壮性 / 注入环境，外加 harness 里对
   `Settings.*` 设备指纹的 override（坑⑫），签名值始终完全由库自算；"补环境"有两层——改 unidbg 源码
   （要重编 jar）和在 harness 里 override JNI（不用重编 jar），能在 harness 解决的优先在 harness 解决。
6. **跨机器的坑只有跨机器才暴露**：`NetLinkSocket`（坑⑪）、`Settings.SCREEN_BRIGHTNESS`（坑⑫）这类
   依赖宿主网络/设备环境的分支，在单一开发机上跑不出来，要靠真实用户的 Windows 实机日志才发现；
   交付物要尽量把这类"未知输入兜底"做扎实。最终用真实服务端 200 + JSON 作为"对不对"的终极裁判。
