# 用 GraalVM Native Image 把 MetasecDump 打包成 exe —— 详细过程与结论

> 目标：把 unidbg 签名 harness（`MetasecDump.java`）编译成原生 exe，最大化逆向难度（无 Java 字节码、机器码级保护），并可被外部 Python 调用（传 `video_id`，写 `<video_id>.json`）。
>
> **最终结论（先说）**：在本机（Windows Server 2022）完成了**完整攻坚**。Native Image **能成功构建出 `--no-fallback` 的纯原生 exe**，且运行时能依次通过 JNA 初始化、加载 dynarmic 后端；**但在"加载 libmetasec_ml.so"这一步，SubstrateVM 触发致命错误 `Fatal error: Must either be at a safepoint or in native mode`**。根因是 **unidbg 的核心与 CPU 后端都重度依赖 JNA**（`com.sun.jna.Structure / Pointer / Callback`），而 **JNA 的 native↔Java 回调与线程状态切换不被 GraalVM SubstrateVM 支持**。这是业界已知的"JNA 不支持 Native Image"硬限制，**非配置可绕过**。因此对本项目，**完整 Native Image 路线不可行**；详见末尾"结论与替代方案"。

---

## 0. 环境与版本

| 项 | 值 |
|---|---|
| OS | Microsoft Windows Server 2022 Standard (10.0.20348) |
| 目标程序 | `full/src/MetasecDump.java` + unidbg 0.9.10-SNAPSHOT（含本地补丁） |
| CPU 后端 | dynarmic（默认）/ unicorn2，均经 **JNA** 调 native |
| GraalVM | **GraalVM CE Java 8 21.3.1**（最后一个支持 Java 8 的 GraalVM 系列；unidbg 在 JDK8 上最稳） |
| native-image 组件 | 21.3.1（手动 `gu install -L` 本地安装） |
| C 工具链 | Visual Studio Build Tools 2022（MSVC 14.44 + Windows SDK 10.0.26100） |
| JNA | 5.10.0（unidbg 自带） |

为什么选 GraalVM **Java 8** 版而不是 JDK17/21 版：unidbg 0.9.10 在 JDK8 上语义最稳；先用 GraalVM CE java8 21.3.1 在 **JVM 模式**验证 harness 能跑通（4.14s、exit=0、6 头齐全），排除"换 JDK 导致 unidbg 跑不起来"的额外变量，再上 native-image。

## 1. 安装 GraalVM + native-image

```bash
# 1) 下载 GraalVM CE java8 21.3.1（Windows）
curl -L -o graalvm.zip \
  https://github.com/graalvm/graalvm-ce-builds/releases/download/vm-21.3.1/graalvm-ce-java8-windows-amd64-21.3.1.zip
unzip -q graalvm.zip      # 解出 graalvm-ce-java8-21.3.1/

# 2) 安装 native-image 组件
#    注意：`gu install native-image`（在线）在本网络下报
#    "A JSONObject text must begin with '{'"（拿不到 Oracle catalog），
#    所以改用"本地 jar 离线安装"：
curl -L -o ni.jar \
  https://github.com/graalvm/graalvm-ce-builds/releases/download/vm-21.3.1/native-image-installable-svm-java8-windows-amd64-21.3.1.jar
graalvm-ce-java8-21.3.1/bin/gu.cmd install -L ni.jar
#    -> 出现 bin/native-image.cmd 即成功
```

## 3. 用 native-image-agent 录制反射/JNI/资源配置

这是主流做法：在 **JVM 模式**跑一遍程序，agent 自动把反射/JNI/资源使用记录成配置文件。

```bash
"$GRAALVM/bin/java.exe" \
  -agentlib:native-image-agent=config-output-dir=native/config \
  -Dunidbg.tgkill.drop=true -cp "build;deps/*" MetasecDump
# 产出 native/config/{reflect-config,jni-config,resource-config,...}.json
```

**坑①：agent 漏掉"只被 native 端 FindClass 的类"。** agent 只能录到 JVM 这一侧观测到的访问；dynarmic 的 `dynarmic.dll` 在 `JNI_OnLoad` 里 `FindClass` 的两个类**没被录到**：
- `com.github.unidbg.arm.backend.dynarmic.DynarmicCallback`（5 个回调方法 `callSVC/handleInterpreterFallback/...`）
- `com.github.unidbg.arm.backend.dynarmic.DynarmicException`（native 端 `throw`，需 `<init>` / `<init>(String)`）

定位方法（从 dll 里抠出它 FindClass 的类名）：

```bash
python -c "import re;d=open('natives/windows_64/dynarmic.dll','rb').read();\
print(sorted(set(re.findall(rb'com/github/unidbg/arm/backend/dynarmic/[A-Za-z0-9/\$]+',d))))"
# -> 只有 DynarmicCallback 和 DynarmicException 两个
```

补一份 `native/config-extra/jni-config.json`（见仓库内该文件），手工登记这两个类及其方法/构造器。

**坑②（致命）：JNA 的"core IDs"无法靠 agent 补全。** 加上上面两个类后，exe 跑到 `==== backend=dynarmic ====` 后报：

```
JNA: Problems loading core IDs: java.lang.Object
```

这是 JNA 的 `Native.initIDs()` 在 native 端（jnidispatch）对一大批"核心类"做 `GetMethodID/GetFieldID`（`java.lang.Object/String/各装箱类型/各种 Buffer/com.sun.jna.*` 等几十项）。agent **没能录到这些极早期、发生在 native 端的 JNI 查找**，所以 jni-config 缺这些核心成员。

解决：用 **GraalVM 官方可达性元数据仓库**里 JNA 的配置（不是 jar 里自带——JNA 的 jar 不含 native-image 元数据，元数据在 oracle/graalvm-reachability-metadata 仓库）：

```bash
# JNA 5.8.0 的统一元数据覆盖到 5.18.x（含 5.10）
curl -s -o reachability-metadata.json \
 https://raw.githubusercontent.com/oracle/graalvm-reachability-metadata/master/metadata/net.java.dev.jna/jna/5.8.0/reachability-metadata.json
```

该文件是**新版统一格式**（只有 `reflection`/`resources`，且 JNI 用 `jniAccessible:true` 内联标注），而 GraalVM 21.3 用**老版拆分格式**（`jni-config.json` + `reflect-config.json`）。写了个转换脚本把 50 条 `reflection` 同时落进 `native/config-jna/{jni-config,reflect-config}.json`，`resources` 落进 `resource-config.json`（详见仓库该目录）。

## 4. 构建命令（`full/native/build-native.bat` 核心）

```bat
call "...\vcvars64.bat"
native-image ^
  -cp "build;deps/*" ^
  -H:ConfigurationFileDirectories=native/config,native/config-extra,native/config-jna ^
  -H:Name=metasecdump -H:Path=native ^
  --no-fallback ^                          REM 必须：否则只是把 JVM 打包进去，毫无保护
  --allow-incomplete-classpath ^           REM 跳过 fastjson/slf4j 的可选缺失类(moneta/log4j)
  --report-unsupported-elements-at-runtime ^
  -H:+ReportExceptionStackTraces ^
  --initialize-at-run-time=com.sun.jna ^
  -Dunidbg.tgkill.drop=true ^
  MetasecDump
```

**坑③：`--allow-incomplete-classpath`。** 不加时分析阶段会因 fastjson 的可选依赖 `org.javamoney.moneta.Money`、slf4j 的 `org.apache.log4j.Level` 等"未解析类型"直接失败。加上后这些被推迟到运行期（用不到就不报）。

**构建结果：成功。** `--no-fallback` 纯原生镜像，约 24–30s 编出 `native/metasecdump.exe`（~47 MB），无字节码残留。

## 5. 运行结果 —— 卡在 JNA/SubstrateVM 线程状态墙

逐步推进（每修一个配置往前走一段）：

1. `NoClassDefFoundError: DynarmicCallback`（native FindClass）→ 补 jni-config 解决；
2. `NoClassDefFoundError: DynarmicException` → 补 jni-config 解决；
3. `JNA: Problems loading core IDs: java.lang.Object` → 引入官方 JNA 元数据解决；
4. **最终（无法绕过）**：

```
==== backend=dynarmic ====
==== loading libmetasec_ml.so ====
Fatal error: Must either be at a safepoint or in native mode
  ... com.oracle.svm.core.util.VMError.guarantee ...
  pendingException = java.lang.IllegalStateException
```

`Must either be at a safepoint or in native mode` 是 SubstrateVM 在 **native↔Java 状态切换不合法**时的断言失败。unidbg 在"加载/重定位 .so + 配置 dynarmic 内存"时，会经由 **JNA 直接映射调用 + native 回调**进出 Java；SubstrateVM 的 JNI/CFunction 线程状态机要求严格的 `@CFunction` 切换，而 **JNA 自己的 native 调用/回调路径不走 SVM 的切换约定**，于是 SVM 判定线程状态非法、`shouldNotReachHere` 直接终止。

这不是某个配置缺失，而是 **JNA 的运行模型与 SubstrateVM 闭世界/线程状态模型根本不兼容**（JNA 官方亦不支持 Native Image，回调尤甚）。而 unidbg 的**核心数据结构（各种 kernel struct）和两个 Windows 后端（dynarmic/unicorn2）都建立在 JNA 之上**，无法在不大改 unidbg/JNA 的前提下规避。

## 6. 结论

- ✅ **可以构建**：GraalVM Native Image 能对 unidbg+MetasecDump 产出 `--no-fallback` 纯原生 exe（这一步本身就达到了"无 Java 字节码、机器码级"保护强度）。
- ✅ **能起步运行**：JNA 初始化、dynarmic 后端加载均已通过（说明 agent + 官方 JNA 元数据 + 手补 dynarmic JNI 配置这套组合是对的）。
- ❌ **无法跑完**：在 .so 加载/内存配置阶段撞上 `Must either be at a safepoint or in native mode`，根因是 **JNA 的 native 回调/线程状态切换不被 SubstrateVM 支持**，且 unidbg 核心与后端**都离不开 JNA**。**纯配置无法绕过。**

**速度旁注**：即便能跑通，Native Image 也只省掉 JVM 启动/JIT 预热那 ~0.5–2s；真正的耗时大头（dynarmic 的 ARM 指令模拟 + ~2s worker pump，均为 native/按真实时钟等待）不会变快。所以"用 Native Image 提速"的收益本来就有限。

## 7. 替代方案（免费、不依赖商业混淆）

1. **把 MetasecDump 最敏感的逻辑下沉到 C 的 JNI 小库**（用本机已装好的 MSVC 编成 dll）：例如 `dispatch()` 的 cmd→返回值映射、那些魔数/特征字符串、y2.a 注册偏移等"知道了就能复刻 harness"的部分。这部分即获得 Nuitka 级（C 机器码）保护；驱动 unidbg 的胶水仍留在 Java。**这是当前约束下最强的免费保护**。
2. **免费 ProGuard 混淆 + Launch4j 包 exe**：ProGuard 做改名/裁剪，强度中等（无字符串加密/控制流平坦化，理论可还原——用户已知其偏弱）；Launch4j 免费把 jar 包成 exe，py 照常调用。胜在零运行风险、速度不变。
3. **维持 JVM + jar 运行**：若可接受不打 exe，签名逻辑的真正机密本就在 `libmetasec_ml.so`（native 黑盒），MetasecDump 仅是环境补全 harness。

> 备注：无论何种打包，运行期都仍需 `libmetasec_ml.so` 与后端 dll 落盘被加载，无法"编进 exe 消失"。

## 8. 实际落地：ZKM 24 字节码混淆（替代 Native Image，已成功）

Native Image 因 JNA/SubstrateVM 不兼容无法跑完（见第 5/6 节）。用户提供了 **ZKM 24（Zelix KlassMaster）商业混淆器**，遂改用它对 `MetasecDump` 做**控制流平坦化 + 字符串加密**——只保护我们自己写的 harness，unidbg 等开源依赖不动。

### 8.1 ZKM 怎么知道混哪个 jar 的哪些类
- `open "MetasecDump.jar";` = **要混淆的目标**（ZKM 把 open 进来的 jar 里所有类拿去混）。
- `classpath "...";` = **仅供解析引用的依赖**（unidbg/jna/fastjson），只读、不混、不改名、不进输出。

### 8.2 调试中踩到并修正的 3 个坑
1. **exclude 语法**：ZKM 的 `exclude` 不是 `class X { }` 花括号块，而是 `and` 连接的排除参数；默认包用 `*`：
   ```
   exclude * and        // 所有类名
           * * and      // 所有字段名
           * *(*);      // 所有方法名   —— 含义=全部"不改名"
   ```
2. **classpath 必须写成一条语句**：ZKM 的多条 `classpath` 语句是**互相覆盖**而非追加，分成 N 条只有最后一条生效，会报 `com.github.unidbg.Module not found`。正确写法是一条语句 + 多个引号串 + 通配符：
   ```
   classpath "C:/.../jre/lib/rt.jar"
             "deps/*.jar";
   ```
   （Windows 路径用正斜杠 `/`，反斜杠在 ZKM 字符串里可能被当转义。）
3. **3 个方法做不了控制流混淆**：`main` 和两个 VaList 版 JNI 分发方法
   （`callObjectMethodV`/`callStaticObjectMethodV`）在 `aggressive`/`normal` 下都会报
   `Inconsistent stack heights / Stack mismatch`（ZKM 流分析器无法分析这几个方法的字节码）。
   用 `obfuscateFlowExclude` 把它们**单独**排除在控制流混淆之外（它们仍会被字符串加密），
   其余所有方法照常做 `aggressive` 流混淆。最终脚本见 `full/zkm/script.zkm`。

### 8.3 最终启用的保护项
```
obfuscate
    obfuscateFlow         = aggressive      // 控制流平坦化
    encryptStringLiterals = flowObfuscate   // 字符串字面量加密（最强档）
    lineNumbers           = delete          // 删行号表
    localVariables        = delete          // 删局部变量名
    ;
```
全部**不改名**（exclude 三行），不破坏 JNI/反射/fastjson。

### 8.4 运行方式与验证
```
# 在 full\ 目录下：
java -jar "ZKM 24.jar" zkm\script.zkm      # 产出 MetasecDump-obf.jar
# 验证混淆后仍能签名：
java -Dbackend=dynarmic -Dpump.seconds=2 -cp "MetasecDump-obf.jar;deps/*" MetasecDump
```
实测：成功混淆 11 个类，混淆后的 jar 用 dynarmic 后端运行，**6 个签名头全部正常产出、退出码 0**。

### 8.5 用 jadx 验证混淆强度（反编译对照）
| 指标 | 原版 jar | 混淆后 jar |
|---|---|---|
| jadx `Code restructure failed`（流无法重建） | 0 | **31** |
| jadx warnings 总数 | 8 | **2331** |
| 明文字符串字面量 | 全明文可读 | **全部消失**，变成 `c[38]` 密文数组下标 |
| 字符串解密器（`static{}`/clinit） | 不存在 | jadx **完全无法反编译**：`Unsupported multi-entry loop pattern ... Please submit an issue!!!` → `throw UnsupportedOperationException("Method not decompiled")` |

结论：方法体被打散成不透明整数 `switch(268435458...)` 状态机、字符串全加密、解密器连 jadx 都无法还原——逆向成本远高于 ProGuard。

## 9. 绿色版打包（解压即用，py 直接调 jar，无需转 exe）

最终交付不走 exe（Python 本就能直接调 jar），而是做一个**内置 JRE 的绿色整包**：

```
metasec-portable/
├─ run.py                 # 入口：内置 jre 驱动混淆 jar → 写 <video_id>.json
├─ MetasecDump-obf.jar    # 混淆后的 harness
├─ jre/                   # 内置 JDK8 运行时（不依赖系统 Java）
├─ deps/                  # unidbg/jna/fastjson 依赖
├─ libs/libmetasec_ml.so  # 被模拟执行的原生库
├─ README.txt  requirements.txt
```

- 用法：`python run.py --video-id <id>` → 离线生成 `<id>.json`（url/body + 6 个签名头 + x-ss-stub）；不联网、不需第三方库、不用装 Java。
- `--send`（需 `httpx[http2]`/`brotli` + 有效 cookie）会真实 POST 并把服务端响应写进同一个 json。
- 运行期：`run.py` 用相对路径定位 `jre/bin/java` 与 `libs/libmetasec_ml.so`，所以**目录结构不能改名/拆散**。
- 速度：每次约 3~6 秒（瓶颈是 native 指令模拟 + 2s 线程泵）。
- 整包构建脚本见 `dist/build-portable.bat`（从本仓库 + 一个 JDK8 的 jre 组装出上面的目录）。

> 仓库里只提交**源文件**（`run.py`/`script.zkm`/kit/文档/打包脚本）；内置 JRE、deps、`.so`、混淆后 jar 等大体积二进制不入库，由打包脚本现场组装。
